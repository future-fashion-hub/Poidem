# Чат компаний: WebSocket-контракт для бэкенда

## Что уже ожидает фронтенд

При `VITE_API_MODE=backend` страница «Мои чаты» сначала получает историю по существующему REST-маршруту:

`GET /api/v1/companies/{companyId}/messages?page=1&limit=100`

Затем открывает постоянное WebSocket-соединение:

`GET /api/v1/ws/companies/{companyId}?access_token=<JWT>`

Базовый URL задаётся в `VITE_CHAT_WS_URL`. Если переменная не задана, фронтенд строит его из `VITE_BACKEND_URL`: например, `http://localhost:8080` превращается в `ws://localhost:8080/api/v1/ws`.

## Авторизация и доступ

- JWT передаётся параметром `access_token`, поскольку WebSocket браузера не поддерживает HTTP-заголовок `Authorization` в handshake.
- Токен следует валидировать так же, как Bearer-токен REST API.
- Подключаться, читать историю и отправлять сообщения может только пользователь, который **уже является участником** компании.
- Для закрытой, заблокированной или удалённой компании соединение нужно отклонять с HTTP `403` или `404` до upgrade.
- Не возвращайте токен в логах, трассировках и сообщениях ошибок.

## Протокол сообщений

Все сообщения — JSON в UTF-8.

### Клиент → сервер: отправка

```json
{
  "type": "message.send",
  "payload": {
    "text": "Встречаемся у входа в 18:30",
    "clientMessageId": "a UUID"
  }
}
```

- `text`: обязательная строка от 1 до 2000 символов после trim.
- `clientMessageId`: UUID для идемпотентности. Повторная отправка того же UUID не должна создавать дубликат.

### Сервер → клиенты компании: новое сообщение

```json
{
  "type": "message.created",
  "payload": {
    "id": 501,
    "companyId": 17,
    "author": {
      "id": 42,
      "firstName": "Анна",
      "lastName": "Иванова",
      "avatarUrl": null
    },
    "text": "Встречаемся у входа в 18:30",
    "createdAt": "2026-10-03T18:02:11+03:00"
  }
}
```

После сохранения сервер рассылает это событие всем активным соединениям данной компании, включая автора. Поля полностью совпадают с типом `CompanyMessage` во фронтенде.

### Сервер → клиент: ошибка

```json
{
  "type": "error",
  "payload": {
    "code": "MESSAGE_TOO_LONG",
    "message": "Сообщение не должно быть длиннее 2000 символов"
  }
}
```

Коды, которые стоит поддержать: `UNAUTHORIZED`, `FORBIDDEN`, `COMPANY_NOT_FOUND`, `MESSAGE_EMPTY`, `MESSAGE_TOO_LONG`, `RATE_LIMITED`.

## Хранение и надёжность

- Сначала сохраняйте сообщение транзакционно в PostgreSQL, затем публикуйте `message.created`.
- Добавьте уникальность `(company_id, author_id, client_message_id)`.
- Историю сортируйте по `createdAt ASC`; pagination нужна и для истории, и для будущей подгрузки старых сообщений.
- Ограничьте частоту отправки, например 10 сообщений за 10 секунд на пользователя.
- При исключении пользователя из компании, блокировке компании или завершении события закрывайте его соединение кодом `1008`.
- Для нескольких экземпляров API используйте общий pub/sub (например PostgreSQL LISTEN/NOTIFY или Redis), иначе участники на разных экземплярах не увидят сообщения друг друга.

## Переменные окружения фронтенда

```env
VITE_API_MODE=backend
VITE_BACKEND_URL=http://localhost:8080
# Необязательно, если путь выше подходит:
# VITE_CHAT_WS_URL=ws://localhost:8080/api/v1/ws
```

После реализации бэкенда чат сразу перейдёт с demo-режима на WebSocket: в шапке чата появится статус «в сети», а поле ввода станет активно.
